# MCP Inspector 2.5.0：测试套件执行报告

## 1. 版本目标

2.5.0 将测试套件当前仅显示成员状态的“执行报告”，升级为可追溯、可下钻、可保存版本的套件报告工作台。

用户应当能够：

- 查看一次套件执行的总体状态、成员结果、真实开始时间、耗时和错误摘要。
- 从套件成员继续下钻到具体 Tool 调用、场景步骤及重试/清理调用。
- 查看每次 Tool 调用最终解析后的参数、响应、协议与时间信息。
- 将一次已结束的执行保存为 `1.0`、`2.0` 等命名报告版本，并在以后重新打开。
- 在并发执行产生多个调用结果时，通过调用列表逐个选择结果，而不是同时渲染多个大型响应区。

本版本不改变测试套件的调度语义，不引入新的测试执行器，也不复制 Tool 调试模块的数据。现有 Suite Execution、Test Execution、Run 和 Workflow Execution 仍是唯一事实来源。

## 2. 当前问题

当前测试套件页底部的执行报告只展示成员名称和通过/失败状态，存在以下缺口：

- 只能查看当前页面内最后一次执行，不能浏览套件执行历史。
- 看不到实际调用参数、响应正文、协议详情和时间线。
- 场景测试包含多个步骤、重试或清理调用时，无法区分具体调用。
- 并发成员完成顺序与套件编排顺序混在一起，无法快速定位失败调用。
- 执行虽然已持久化，但用户无法将某次执行标记为 `1.0`、`2.0` 等稳定报告版本。
- 历史报告若继续使用当前测试用例名称或定义，会被后续改名和编辑影响。

## 3. 核心决策

### 3.0 产品方案比较

针对“并发成员产生多个 Tool 调用结果”的展示，有三种可行方向：

| 方案 | 用户价值 | 实现与性能 | 主要问题 | 结论 |
| --- | --- | --- | --- | --- |
| 全部行内手风琴 | 上下文连续，第一眼容易理解 | 初版较快 | 多层展开后页面极长；多个大 JSON 同时渲染；并发越高越难定位 | 不采用 |
| 独立全屏报告页 | 空间充足，适合历史和复杂排查 | 路由与状态清楚 | 用户每次执行后都要离开套件编辑上下文 | 单独使用不够好 |
| 主从双栏查看器 | 调用导航与详情关系稳定；一次聚焦一个结果 | 可按需加载且复用 Tool 响应区 | 窄屏需要退化布局 | 作为核心组件 |

最终采用混合方案：

- **套件页是“即时诊断入口”**：执行后在当前页看到摘要和主从双栏报告，不强迫离开编排上下文。
- **测试报告页是“历史资产入口”**：浏览所有批次和 `1.0`、`2.0` 等保存版本，适合长期追溯。
- 两个入口复用同一个报告查看器和同一数据契约，避免行为分叉。

这个方案直接服务两类核心任务：执行后快速找到失败原因，以及过一段时间后准确还原某个发布版本的测试证据。

### 3.1 三层浏览模型

执行报告采用“报告批次 → 套件成员/调用 → 单一调用详情”三层模型：

```text
报告历史 / 已保存版本
        │
        ▼
套件成员（按快照顺序）
        │ 展开
        ▼
步骤、重试与清理调用列表
        │ 选择一个
        ▼
单一详情面板：参数 + Tool 调试式响应区
```

- 第一层选择一次套件执行，或一个指向该执行的已保存版本。
- 第二层保持套件快照中的成员顺序；成员可展开/收起，展开后显示该成员产生的调用列表。
- 第三层始终只展示一个选中调用的详情，并复用 Tool 调试响应区的能力。

成员展开是导航行为，不在成员行内直接渲染完整 JSON 响应。这样可以支持任意数量的并发结果，同时避免多个响应编辑器同时占用页面和内存。

### 3.2 并发结果展示

套件并发数仍由现有配置控制。报告展示遵循以下规则：

- 成员主列表按保存时的套件成员位置排序，结果不会因并发完成顺序而跳动。
- 每行显示状态、调用数、真实开始时间和耗时；并发关系可由重叠时间判断。
- 展开成员后，调用按场景步骤位置、尝试次数和记录 ID 稳定排序；同时保留实际开始时间。
- 默认选中第一个失败/错误调用；全部通过时选中第一个可查看调用。
- 用户可以展开多个成员以浏览导航树，但右侧只保留一个详情选择。
- 执行过程中显示运行中、等待中和已完成状态；尚未生成 Run 的项不显示伪造详情。
- 切换报告或调用时，中止或隔离旧请求，迟到响应不得覆盖当前项目、套件、执行或调用。

2.5.0 不提供多响应并排对比。报告版本差异对比可在后续版本单独设计。

这里的套件“并发数”表示同时调度多少个套件成员，不表示自动把同一成员重复运行多次。某个成员出现多个结果，主要来自场景步骤、重试和清理调用；它们统一进入该成员的调用列表。若未来增加按次数重复执行，应该在成员和调用之间新增“迭代批次”层，不能复用 attempt 冒充重复执行。

### 3.3 报告历史与保存版本

“历史”和“保存”是两个不同概念：

- 每次套件执行自动成为持久化历史记录，无需用户手动保存。
- “保存报告”创建一个轻量、不可变内容的命名版本，引用某次已结束的套件执行。
- 保存版本包含名称、版本标签、备注和创建时间，例如 `发布前基线 / 1.0`、`参数改造后 / 2.0`。
- 保存版本不深拷贝参数和响应；它通过引用保护 Suite Execution → Test Execution → Run 执行链。
- 报告内容来自执行时快照，不受后续套件、用例改名或编辑影响。
- 删除保存版本只删除版本标记，不删除原执行历史；清理历史时必须保留仍被保存版本引用的执行链。

同一项目、同一套件内，规范化后的版本标签必须唯一。冲突返回 `409 REPORT_VERSION_CONFLICT`，不自动覆盖旧版本。

界面动作建议命名为“保存为版本”，并在辅助文案中说明“所有执行已自动保留”。这可以避免用户误以为未点击保存就会丢失执行结果。

### 3.4 详情内容

选择一个 Tool 调用后，详情至少展示：

- 上下文：套件、测试用例、场景步骤、尝试次数、Run ID、Workflow Execution ID。
- 状态：等待、运行、通过、失败、错误、取消、跳过。
- 请求：执行时最终解析后的 Tool 参数，以只读 JSON 查看。
- 响应：复用 `RunResultPanel` 的概览、详细、HTTP、RPC、时间线和 Workflow 能力；只显示该 Run 实际存在的视图。
- 错误：标准化错误码、阶段和安全错误摘要。
- 时间：排队、开始、结束和耗时。
- 断言：所属测试步骤的断言结果；断言不伪装成 Tool 响应。

参数和响应只读展示。查看历史不得修改当前 Tool 调试 Tab；如以后提供“加载到调试”，必须是显式操作。

## 4. 页面与交互

### 4.1 测试套件页

套件编辑区下方保留“执行报告”，升级为可折叠工作台：

```text
┌ 执行报告 ─ 最新执行 / 已保存 2.0 ─ [保存报告] [在测试报告中打开] ┐
│ 通过  2/2 成员  5 次调用  1.42s                                  │
├──────────────────────────────┬───────────────────────────────────┤
│ ▾ 查询 price_rule  通过 2调用 │ 调用上下文 / 最终参数             │
│   ● 查询规则 / 第1次          │ ┌ 请求与结果 详细 HTTP RPC 时间线 ┐│
│   ● cleanup / 第1次           │ │ Tool 调试式响应区               ││
│ ▸ 查询店铺       通过 1调用   │ └─────────────────────────────────┘│
└──────────────────────────────┴───────────────────────────────────┘
```

- 报告可整体折叠，避免挤压套件编辑表单。
- 报告历史选择器显示状态、执行时间、耗时和保存版本标签。
- 运行结束后提供“保存报告”；运行中不能保存。
- 保存成功后当前报告仍保持选中，不自动切换页面。

### 4.2 测试报告页

现有“测试报告”增加“测试用例 / 测试套件”视图切换：

- 测试用例保留现有列表和详情行为。
- 测试套件列出普通执行历史，并突出显示已保存版本。
- 选择记录后使用与套件页相同的报告查看器。
- 支持按套件、状态、保存状态和版本标签筛选。
- 历史列表与详情分别拥有明确滚动容器，页面本身不产生嵌套无限滚动。

### 4.3 保存报告对话框

字段：

- 报告名称：必填，1–120 个字符。
- 版本标签：必填，1–40 个字符，例如 `1.0`、`2.0-rc1`。
- 备注：可选，最多 500 个字符。

提交前显示套件名称、执行时间、状态和 Suite Revision。保存失败保留用户输入并在字段或对话框内显示可恢复错误。

## 5. 领域与共享契约

新增共享类型，使用现有 Zod 契约贯穿服务端与客户端：

```ts
type TestSuiteExecutionReportOutline = {
  execution: TestSuiteExecutionDetail;
  members: Array<{
    item: TestSuiteExecutionItem;
    testExecution: TestExecutionSummary | null;
    calls: Array<{
      stepRecordId: string;
      stepId: string;
      stepKind: "tool" | "cleanup";
      attempt: number;
      runId: string | null;
      workflowExecutionId: string | null;
      status: TestExecutionStepStatus;
      startedAt: string | null;
      completedAt: string | null;
      durationMs: number | null;
      error: SafeExecutionError | null;
    }>;
  }>;
};

type SavedTestSuiteReport = {
  id: string;
  projectId: string;
  suiteId: string;
  suiteExecutionId: string;
  name: string;
  versionLabel: string;
  note: string | null;
  revision: number;
  createdAt: string;
  updatedAt: string;
};
```

报告 Outline 只返回导航所需摘要，不重复返回完整 Run 响应。选中调用时，再通过既有项目隔离 API 按需加载 Test Execution 和 Run。

历史显示名称必须以 `suiteSnapshot`、`definitionSnapshot` 为准；当前定义仅用于提供仍然有效的导航链接。

## 6. 服务端接口

### 6.1 套件执行历史

```http
GET /api/projects/:projectId/test-suites/:suiteId/executions?cursor=&limit=
GET /api/projects/:projectId/test-suite-executions/:executionId/report
```

- 历史接口采用稳定的 `createdAt + id` 游标分页。
- `report` 返回 Outline，服务端验证 Suite Execution、Test Execution、Step 和 Run 的项目及引用链。
- 完整响应继续由既有 `getTestExecution` 和 `getRun` 按需读取，不新增包含所有响应的巨型接口。

### 6.2 保存报告

```http
GET    /api/projects/:projectId/test-suite-reports?suiteId=&cursor=&limit=
POST   /api/projects/:projectId/test-suite-reports
GET    /api/projects/:projectId/test-suite-reports/:reportId
PATCH  /api/projects/:projectId/test-suite-reports/:reportId
DELETE /api/projects/:projectId/test-suite-reports/:reportId
```

POST 请求体：

```json
{
  "suiteId": "suite-id",
  "suiteExecutionId": "execution-id",
  "name": "发布前基线",
  "versionLabel": "1.0",
  "note": "首个稳定版本"
}
```

约束：

- POST 使用 `Idempotency-Key`；同键同载荷重放返回同一报告，不同载荷返回冲突。
- 只能保存终态执行，且执行必须属于请求项目和请求套件。
- PATCH 只修改名称、版本标签和备注，并使用 `revision` 做乐观并发控制；不得改指向的执行。
- 所有错误返回稳定错误码，不在普通日志、Toast 或 URL 中包含参数、响应和凭据。
- 删除是明确确认后的版本标记删除；不级联删除执行链。

## 7. 数据持久化

实现前重新检查最新迁移号，新增下一编号迁移，不修改任何已发布迁移。计划新增：

```sql
saved_test_suite_reports (
  id,
  project_id,
  suite_id,
  suite_execution_id,
  name,
  version_label,
  version_label_normalized,
  note,
  revision,
  created_at,
  updated_at
)
```

关键约束：

- `(project_id, suite_id, version_label_normalized)` 唯一。
- 使用复合外键保证套件、执行和保存报告属于同一项目。
- `suite_execution_id` 使用限制删除语义，不能因清理历史破坏已保存版本。
- 不存储完整参数、响应或凭据副本。
- 现有被 Test Execution 引用的 Run 保留规则必须覆盖已保存执行链。
- SQLite 升级必须保留全部既有数据，并验证 source/dist 迁移字节一致。

## 8. 客户端状态与性能

- 查询键必须包含 `projectId + suiteId + suiteExecutionId`；调用详情再包含 `testExecutionId + runId`。
- 项目或连接切换时清空不兼容选择，并使用 abort/generation token 拒绝迟到响应。
- 每个套件保留最近选择的报告、展开成员和选中调用，但不得跨项目复用。
- 首屏仅加载报告历史和 Outline；完整 Run 在用户选择调用时加载。
- 最近详情可使用有界 LRU 缓存；缓存键包含项目和 Run ID，项目切换即清理。
- 大 JSON 继续使用现有只读 JSON/文本查看能力，不创建第二套响应渲染器。
- 目标：100 个成员、每成员 20 次调用时，Outline 仍可导航；任何时刻最多挂载一个完整响应查看器。

## 9. 安全与隐私

- 原始响应沿用现有 Run 查看权限与脱敏规则；保存版本不会产生新的响应副本。
- 报告名称、版本标签、备注均视为不可信输入，输出时转义，禁止 HTML 注入。
- 导出能力不在 2.5.0 范围；不得通过默认导出间接带出保存报告响应。
- Run ID、Test Execution ID 和 Suite Execution ID 不能只凭客户端传值建立关系，服务端必须核对引用链。
- 同 URL 的不同连接仍按 connection ID 和运行身份隔离；报告不得借由 URL 合并结果。
- 普通埋点只记录状态、计数和耗时，不记录 Tool 参数或响应。

## 10. 可访问性与国际化

- 成员展开按钮使用原生 button，并提供 `aria-expanded`、`aria-controls` 和明确焦点样式。
- 状态不能只依靠颜色，必须同时提供图标和文本。
- 列表、对话框、Tabs 和详情区域支持键盘操作；关闭对话框后焦点返回触发按钮。
- 运行中状态使用非侵入式 `aria-live="polite"`；响应内容更新不反复抢占读屏焦点。
- 所有新增文本覆盖 `zh-CN` 和 `en-US`。
- 遵循现有 UI token、Phosphor 图标和高密度 DevTools 布局，不引入新的设计系统。

## 11. 状态与错误语义

- 套件、成员和调用沿用现有状态集合；父级状态由持久化执行结果决定，不由客户端重新推算覆盖。
- 取消中的已完成调用仍可查看；未开始成员显示跳过或取消原因。
- 报告 Outline 缺少某个历史 Run 时，成员仍可显示，详情呈现 `REPORT_RUN_UNAVAILABLE`，其他调用不受影响。
- 被删除或改名的当前测试用例仍按执行快照展示，并标记“当前定义不可用”。
- 保存运行中报告返回 `REPORT_EXECUTION_NOT_TERMINAL`。
- 跨项目、跨套件、错误 Run 归属和已删除报告均返回不泄露存在性的安全错误。

## 12. 非目标

2.5.0 不包括：

- 两个报告版本的字段级响应 Diff 或并排比较。
- 修改、重放或从历史响应直接覆盖当前 Tool 调试参数。
- 新的套件调度算法、负载测试统计或分位数图表。
- 将完整报告默认导出为文件。
- AI 自动分析失败原因；该能力属于后续 Agent 版本。

## 13. 验收场景

1. 单 Tool 成员执行成功后，可以看到最终参数和完整 Tool 响应视图。
2. 场景成员含多个步骤、一次重试和清理调用时，展开成员可看到全部调用，选择任一调用只更新单一详情区。
3. 并发运行 8 个成员时，成员顺序稳定、状态实时更新、完成顺序和耗时准确，页面不会同时挂载 8 个响应区。
4. 失败套件默认定位到首个失败调用，错误、请求和已有响应可独立查看。
5. 将同一次执行保存为 `1.0` 后可重新打开；再次保存 `1.0` 返回明确冲突；可另存为 `2.0`。
6. 套件和用例随后改名，`1.0` 报告仍显示执行时快照名称与修订号。
7. 删除 `1.0` 只删除保存标记，普通历史仍可打开；受保存报告保护的执行链不能被历史清理破坏。
8. 快速切换项目、套件、报告和调用，迟到请求不会串入当前详情。
9. 同 URL、不同凭据的连接生成的执行报告不能互相读取。
10. 已知秘密夹具不会出现在 URL、普通日志、Toast、埋点或新增数据库列中。

## 14. 发布门槛

- 新增共享契约、仓储、服务、路由、客户端和 UI 测试全部通过。
- 套件历史、Outline、保存版本及引用保护的集成测试通过。
- 并发、取消、缺失 Run、改名/删除定义和迟到响应回归通过。
- 100 × 20 调用 Outline 性能夹具通过，任一时刻只挂载一个完整响应查看器。
- `zh-CN` / `en-US`、键盘、焦点、读屏状态和浅色/深色检查通过。
- `npm run verify`、发布制品迁移检查和 `git diff --check` 通过。
