# 受控压力测试

## Problem Statement

如何让 MCP Inspector 用户复用已经验证过的单 Tool 或场景测试，对真实 MCP Server 做可解释、可停止、不会意外失控的本地压力验证？

## Recommended Direction

2.5.1 新增独立的“压力测试”模块。压力目标是一条已保存的测试用例：单 Tool 用例用于接口压测，场景用例用于完整业务流压测。测试套件仍负责功能回归编组，不作为首版压力目标，避免虚拟用户并发与套件成员并发相乘。

首版采用闭环负载模型：虚拟用户在升压后持续循环执行目标用例，并在每轮之间等待思考时间。系统保存聚合指标和有界代表性样本，提供实时状态、停止、阈值判定和历史报告；它是桌面端单节点预发布验证工具，不宣称替代分布式容量平台。

## Key Assumptions to Validate

- [x] 用户已有可复用的单 Tool 或场景测试，不需要在压测模块重新编排业务流程。
- [ ] 1–20 个本地虚拟用户和最多 1,000 次迭代足以覆盖首版预发布回归场景。
- [ ] 聚合指标加失败、慢调用和少量成功样本足以完成大部分诊断，不需要在报告里浏览每个完整响应。

## MVP Scope

- 压测方案 CRUD，目标为已保存测试用例。
- 固定虚拟用户、升压时间、持续时间、思考时间和最大迭代数。
- 错误率、P95 和最低 RPS 阈值。
- 单项目最多一个活动压测；显式确认破坏性 Tool。
- 实时汇总、取消、自动熔断、历史报告和有界样本详情。
- 所有外部输入使用共享 Zod 契约，所有数据按项目 ID 隔离。

## Not Doing (and Why)

- 测试套件作为压力目标——嵌套并发会放大实际负载且指标归属不清。
- 固定 RPS 开环调度——需要独立的到达率调度器和背压模型，留给后续版本。
- 任意多阶段曲线——首版先验证闭环虚拟用户模型。
- 分布式压测——桌面 Inspector 没有跨节点时钟、协调和结果归并能力。
- 报告 Diff——2.5.1 先建立可信单次报告，趋势比较单独规划。
- 永久保留无限完整响应——避免 SQLite、内存和界面被高基数数据拖垮。

## Open Questions

- 真实用户是否需要超过 20 个虚拟用户或 1,000 次迭代；用首版实际使用数据再调整上限。
- 后续应优先支持固定 RPS，还是支持测试套件/数据集驱动迭代。
